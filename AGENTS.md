# Инструкции проекта для Codex App

## Язык взаимодействия
- Общайся с пользователем и составляй отчёты на русском языке.
- Архитектурные решения, планы, замечания и результаты проверок описывай по-русски.
- Имена классов, методов, интерфейсов, переменных, файлов, CLI-команды и ключи конфигурации оставляй на английском.
- Не переводи диагностические сообщения, вывод команд, названия библиотек и API.
- Комментарии в коде пиши по-русски, только если они действительно объясняют неочевидную логику.

## Технологии и архитектура
- Backend: C# / ASP.NET Core; frontend: React + TypeScript; предпочтительная БД: **PostgreSQL**; SQL Server допускается как альтернатива при явном требовании.
- Доступ к БД: **ADO.NET через Npgsql для PostgreSQL**; для специально выбранного SQL Server — `Microsoft.Data.SqlClient`. Никаких ORM.
- **Запрещены любые ORM и micro-ORM**, включая EF Core, EF6, Dapper, NHibernate. Запрещены ORM-миграции.
- Учитывай существующую архитектуру; применяй асинхронные операции, параметризованный SQL и явное преобразование `DbDataReader` в DTO.
- Вводи слои Repository/Service только если они реально упрощают приложение.
- Никогда не подставляй пользовательские значения конкатенацией в SQL; для динамических SQL-идентификаторов используй белые списки.

## Мультиагентная координация
Пользовательские роли: `architect`, `developer`, `test-engineer`, `reviewer`, `documentation`.
- Для сложных функций: `architect` (анализ без записи) → `developer` (реализация) → `test-engineer` + `reviewer` (независимые проверки) → исправления `developer` → повторная проверка → `documentation` (актуализация документов по проверенному коду).
- Для маленьких исправлений выбирай только нужных агентов; не делегируй без необходимости.
- Для изменений API, схемы БД, инфраструктуры и архитектурных решений обновление документации обязательно. Для мелких изменений без влияния на контракты проверь необходимость документации и при отсутствии изменений объясни почему.
- Документация должна отражать реализованный и проверенный код; не выдавай план за готовую функциональность.
- Агент `documentation` может редактировать `README.md` и `docs/**`; не назначай в этот момент другим агентам те же файлы.
- Главный Codex должен запускать **реальные потоки подагентов**, а не изображать их. Если роль недоступна, сообщи об этом.
- Параллельно выполняй независимые исследования и проверки. Не разрешай двум агентам одновременно изменять одни файлы.
- Для агентов, которые пишут файлы, назначай отдельные области ответственности.
- Инструкция «не изменять файлы» — правило поведения, а **не техническое ограничение прав ОС**.

## Podman и базы данных (только локальная среда)
- По умолчанию используй **PostgreSQL 17** в сервисе `postgres` Podman Compose (`127.0.0.1:15432`). SQL Server доступен только как необязательный профиль `sqlserver` (`127.0.0.1:14333`). Не переключай СУБД без требования задачи.
- Для чтения или редактирования исходного кода Podman не обязателен: не запускай его без необходимости.
- Если тестам или разработке нужны сервисы, разрешено смотреть статусы и логи, запускать, перезапускать и останавливать **только контейнеры этого проекта**.
- Не перезапускай работающий сервис без причины; не трогай чужие контейнеры.
- Запрещено автоматически выполнять `compose down -v`, `volume rm/prune`, `system prune` и другие разрушительные операции.
- `app_dev` — локальная рабочая БД PostgreSQL, создаваемая при **первой инициализации пустого тома** через `POSTGRES_DB`: удаление данных, сброс или изменение схемы только после явного одобрения. В существующем томе смена переменной `POSTGRES_DB` не создаёт новую БД.
- `app_tests` — планируемая изолированная тестовая БД, **не создаётся автоматически**. Создавать её можно после проверки локального экземпляра и изоляции; перед очисткой перепроверяй целевую БД.
- Проверяй PostgreSQL через `pg_isready`, затем при необходимости реальным SQL-подключением и `SELECT 1`; `running` сам по себе не гарантирует готовность. Для SQL Server аналогично проверяй подключение, а не только статус.
- Не выполняй непроверенные SQL-скрипты и не сохраняй секреты в Git.

## Безопасность и подтверждения
- Не выполняй деплой, публикацию, доступ к production и изменения production-БД без отдельного явного разрешения.
- Не обходи подтверждения Codex App и ограничения sandbox. Эти инструкции не являются механизмом контроля доступа.
- Запрашивай подтверждение перед удалением постоянных томов, данных или контейнеров с сохраняемыми данными.
- Не выполняй действия с ресурсами вне проекта без явного разрешения.
- Сохраняй пользовательские изменения, не перезаписывай их без проверки.

## Критерии готовности
- По возможности собирай затронутое приложение; запускай подходящие тесты и честно указывай результаты.
- `reviewer` независимо анализирует реальные изменения, проверяет отсутствие ORM и соблюдение приоритета PostgreSQL.
- `documentation` актуализирует соответствующие документы после проверки реализации, когда изменились интерфейсы, схемы, инфраструктура или приняты архитектурные решения.
- При закрытии задачи обязательно сообщи, обновлена ли документация и почему.
- Если проверка недоступна, объясни причину; не выдавай её за выполненную.
- Финальный отчёт по-русски: запущенные агенты; решения; изменённые файлы; команды сборки/тестирования с результатами; замечания ревью; риски; действия с инфраструктурой.

## Начало работы
- Сначала изучи `README.md`, `docs/architecture.md` и актуальные ADR в `docs/decisions/`.
- Если в репозитории пока только этот шаблон, не придумывай бизнес-приложение самостоятельно. Работай по явно поставленной задаче.


## Стиль документации
Все Markdown-документы проекта должны быть написаны
в строгом техническом стиле.

Требования:
- Только русский язык, кроме технических терминов.
- Без обращения к читателю.
- Без разговорных и эмоциональных формулировок.
- Без вводных фраз и искусственных заключений.
- Без эмодзи и декоративных элементов.
- Короткие, конкретные предложения.
- Минимум текста, максимум практической информации.
- Только проверенные команды и фактические сведения.
- Отсутствие повторений и очевидных пояснений.

README.md — инструкция по установке, настройке,
запуску и проверке приложения.

Не превращать README.md в описание процесса
разработки или отчёт о выполненной работе.

Documentation Agent отвечает за соблюдение
этого стиля при обновлении документации.
