# ДЗ №5. Шардирование диалогов

## Выбор ключа шардирования

В качестве ключа шардирования я выбрал пару UUID участников, отсортированную по возрастанию. API объединяет UUID в 32 байта в сетевом порядке и вычисляет SHA-256. Первые четыре байта хеша интерпретируются как беззнаковое число в сетевом порядке. Остаток от деления на 1024 даёт номер виртуального бакета от 0 до 1023. Бакет — логическая группа диалогов. Его номер остаётся прежним при добавлении физического шарда.

Оба направления переписки дают одну пару UUID и один бакет. При шардинге по отправителю сообщения активного пользователя концентрировались бы на одном узле, а его ответы и входящие сообщения могли бы храниться на разных узлах. Ключ из пары распределяет диалоги активного пользователя по разным узлам, если он пишет разным собеседникам. При шардинге по UUID сообщения чтение одного диалога потребовало бы опросить все узлы. В выбранной схеме API обращается только к шардам, которые обслуживают или ранее обслуживали бакет. Один особенно активный диалог ограничен пропускной способностью одного узла на запись.

## Маршрутизация чтения и записи

В основном PostgreSQL таблица `dialog_routes` хранит строки `(bucket, generation, shard)`. Поколение — номер версии карты. Карта задаёт, на какой физический шард направлять записи для каждого бакета. При переключении в таблицу добавляется новая версия карты, а предыдущие строки сохраняются для чтения истории.

- `send` берёт для бакета строку с наибольшим `generation` и выполняет один `INSERT` на указанном шарде.
- `list` получает все маршруты бакета и читает переписку на каждом уникальном шарде по первым трём полям первичного ключа `(bucket, user_low, user_high, message_id)`. API объединяет результаты, убирает дубликаты по UUID сообщения и сортирует по времени записи и UUID. Объём памяти при чтении зависит от размера полной истории.

Например, у бакета `8` исходный маршрут `(8, 1, dialog-a)`. После переключения добавляется `(8, 2, dialog-c)`. Новые сообщения идут в `dialog-c`, ранее записанные остаются в `dialog-a`. Запрос истории читает оба шарда и возвращает один список. Если в обеих версиях указан один и тот же шард, API обращается к нему один раз.

## Запуск

Стенд использует Compose-проект `social-network-homework-5` с отдельными томами. Сервис `postgres` хранит пользователей и маршруты. `dialog-a`, `dialog-b` и `dialog-c` хранят сообщения в отдельных экземплярах PostgreSQL 17. Сервис `api` доступен на `127.0.0.1:5085`. Третий шард подготавливается одновременно с остальными и получает маршруты при переключении.

Для запуска требуются Docker Compose или Podman с провайдером Compose и [файл `.env`](../../README.md#настройка). `POSTGRES_DB_HW5` и `API_HOST_PORT_HW5` задают имя базы каталога и порт API. Значения по умолчанию — `app_dialogs` и `5085`. Следующие команды выполняются из корня проекта в PowerShell.

```powershell
docker compose -p social-network-homework-5 --env-file .env -f infrastructure/homework-5/compose.yaml up -d --build
```

Для Podman используется `podman compose` с теми же аргументами. При установленном отдельно провайдере `podman-compose` используется `python -m podman_compose`. Явный параметр `-p` имеет приоритет над `COMPOSE_PROJECT_NAME` в `.env`.

## Проверка через Swagger UI

1. Открыть [Swagger UI](http://127.0.0.1:5085/swagger/index.html). Зарегистрировать двух пользователей через `POST /user/register` и сохранить оба UUID.
2. Выполнить `POST /login` с UUID и паролем первого пользователя. Ввести значение `token` в **Authorize** без префикса `Bearer`.
3. Выполнить `POST /dialog/{user_id}/send` с UUID второго пользователя и телом `{"text":"Сообщение из Swagger UI"}`.
4. Выполнить `GET /dialog/{user_id}/list` с UUID второго пользователя. Сверить отправителя, адресата и текст.

Я проверил оба метода через Swagger UI. Отправка вернула `200` с `Content-Length: 0`. При чтении я получил `200` и сверил отправителя, адресата и текст в полях `from`, `to` и `text`. В сгенерированной схеме OpenAPI для отправки указаны обязательное поле `text` и ответы `200`, `400`, `401`, `503`.

## Переключение записей на третий шард

В поколении 1 чётные бакеты назначены `dialog-a`, нечётные — `dialog-b`. Поколение 2 переводит бакеты с `bucket % 3 = 2` на `dialog-c`. Для остальных бакетов сохраняется прежний владелец.

Для автоматизированного воспроизведения на стенде Podman запустить первую фазу до переключения. Скрипт создаёт отдельные тестовые анкеты и подбирает диалог для перемещаемого бакета. Состояние между фазами хранится в `TestResults/hw5-integration/state.json`.

```powershell
python scripts/homework-5.py before
```

Применить [скрипт переключения](../../infrastructure/homework-5/activate-third-shard.sql) на каталоге. Публикация поколения выполняется в одной транзакции и не требует перезапуска API. Повторное применение сохраняет опубликованные строки.

```powershell
podman exec social-network-homework-5_postgres_1 sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -f /homework-5/activate-third-shard.sql'
```

На Docker Compose вместо `podman exec social-network-homework-5_postgres_1` используется `docker compose -p social-network-homework-5 --env-file .env -f infrastructure/homework-5/compose.yaml exec -T postgres`.

Проверить карту и запустить вторую фазу на стенде Podman.

```powershell
podman exec social-network-homework-5_postgres_1 sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT generation, shard, count(*) FROM dialog_routes GROUP BY 1, 2 ORDER BY 1, 2"'
```

```powershell
python scripts/homework-5.py after
```

Я применил скрипт переключения и сверил карту запросом к PostgreSQL. Первая транзакция добавила 1024 маршрута, повторная — 0.

| Поколение | `dialog-a` | `dialog-b` | `dialog-c` |
| --- | ---: | ---: | ---: |
| 1 | 512 | 512 | 0 |
| 2 | 341 | 342 | 341 |

До переключения я запустил автоматизированную проверку `before`. Она подтвердила `401` без токена, `400` для недопустимых запросов, пустую историю, изоляцию диалогов и доступ к переписке с обеих сторон. По SQL я проверил, что сообщения одного отправителя разным собеседникам записались на два шарда.

| Фаза | `dialog-a` | `dialog-b` | `dialog-c` |
| --- | ---: | ---: | ---: |
| `before` | 1 | 1 | 0 |
| `after` | 1 | 1 | 1 |

После переключения я запустил фазу `after`. Оба участника получили исходную историю и новое сообщение. По SQL я подтвердил запись нового сообщения на `dialog-c`. Дополнительная автоматизированная проверка зафиксировала смену поколения и 281 успешный `GET` с интервалом около 200 мс. Ошибок при чтении не было.

## Физический перенос истории без остановки

На стенде я проверил переключение маршрута записи при сохранении истории на прежнем шарде. Запрос отправки, прочитавший карту до фиксации поколения, может завершиться на предыдущем владельце. Физический перенос истории я описал как эксплуатационную процедуру. На стенде этот этап не выполнялся.

1. Подготовить целевой PostgreSQL с той же схемой и добавить его в конфигурацию всех API-реплик. Для непрерывного обслуживания нужны минимум две реплики за балансировщиком, общий постоянный набор ключей ASP.NET Core Data Protection и одинаковый идентификатор приложения. На время процедуры выполнять изменения карты последовательно.
2. Опубликовать новое поколение одной транзакцией. Последующие запросы записи направляются новому владельцу. Поочерёдно вывести каждую реплику API из балансировщика, дождаться завершения её активных запросов без принудительной отмены и вернуть реплику в обслуживание. Проверить завершение всех операций, которые могли получить старый маршрут, включая записи вне API, если они существуют.
3. Перенести строки бакета пакетами с сохранением первичного ключа, отправителя, текста и времени. Повторная вставка игнорирует конфликт по первичному ключу. Проверить наличие и совпадение содержимого каждой исходной строки на целевом узле. Чтение на этом этапе обращается к обоим владельцам и устраняет дубликаты по UUID сообщения.
4. В одной транзакции перенаправить исторические маршруты бакета с источника на целевой шард. Повторить поочерёдный вывод и возврат API-реплик для завершения чтений, начатых по старой карте. Проверить чтение переписки с обеих сторон.
5. Сохранить исходные строки до окончания окна отката. В этом окне исторические маршруты можно вернуть после проверки источника, сохранив текущий маршрут записи. Удаление исходных строк допускается после проверки чтений и закрытия окна отката.
