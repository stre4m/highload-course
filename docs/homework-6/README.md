# ДЗ №6. Онлайн-обновление ленты новостей

## Запуск

Требуются Podman с провайдером Compose или Docker Compose и свободные порты `5086`, `5087`, `15676`. Команды выполняются из корня репозитория.

При первом запуске создать файл `.env.hw6` в текстовом редакторе. Для каждого сервиса задать отдельный пароль. Для RabbitMQ использовать буквы и цифры, поскольку пароль подставляется в AMQP URL.

```dotenv
POSTGRES_USER=appuser
POSTGRES_PASSWORD=ReplaceWithPostgresPassword
RABBITMQ_PASSWORD_HW6=ReplaceWithRabbitMqPassword
```

```text
podman compose --env-file .env.hw6 -f infrastructure/homework-6/compose.yaml build api
podman compose --env-file .env.hw6 -f infrastructure/homework-6/compose.yaml up -d --no-build
```

Для Docker Compose используется префикс `docker compose` с теми же аргументами.

| Компонент | Адрес |
| --- | --- |
| Swagger, первый экземпляр | [127.0.0.1:5086](http://127.0.0.1:5086/swagger/index.html) |
| Swagger, второй экземпляр | [127.0.0.1:5087](http://127.0.0.1:5087/swagger/index.html) |
| RabbitMQ Management | [127.0.0.1:15676](http://127.0.0.1:15676/) |

Для RabbitMQ Management используются пользователь `feed` и пароль `RABBITMQ_PASSWORD_HW6` из `.env.hw6`. База `app_feed` создаётся в отдельном томе при первой инициализации. [Схема доставки](../decisions/0006-feed-delivery.md) использует один брокер RabbitMQ и PostgreSQL.

## Ручное повторение

1. Через Swagger зарегистрировать автора, получателя и контрольного пользователя. Получить токены через `POST /login`. Формат регистрации приведён в [описании API](../api.md#регистрация).
2. В Swagger авторизоваться как получатель и выполнить `PUT /friend/set/{user_id}` с UUID автора. Контрольный пользователь сохраняет пустой список друзей.
3. В WebSocket-клиенте с поддержкой заголовков, например Postman, открыть три соединения. Перед подключением задать заголовок `Authorization: Bearer <токен>`.
   - `ws://127.0.0.1:5086/post/feed/posted` с токеном получателя.
   - `ws://127.0.0.1:5087/post/feed/posted` с тем же токеном.
   - `ws://127.0.0.1:5087/post/feed/posted` с токеном контрольного пользователя.
4. В Swagger сменить токен на токен автора. Выполнить `POST /post/create` с телом `{"text":"Проверка WebSocket"}`. Зафиксировать UUID из ответа.
5. Проверить входящие кадры в WebSocket-клиенте. В обоих соединениях получателя `postId` совпадает с UUID созданного поста. Контрольное соединение остаётся открытым и кадр не получает.
6. В Swagger запросить `GET /post/feed` с токеном получателя и контрольного пользователя. Сверить присутствие поста только у получателя.

Проверка инфраструктуры.

```text
podman exec social-network-homework-6-postgres-1 pg_isready -h 127.0.0.1 -d app_feed
podman exec social-network-homework-6-postgres-1 psql -U appuser -d app_feed -Atc "SELECT 1, to_regclass('feed_outbox'), to_regclass('feed_targets');"
podman exec --user rabbitmq social-network-homework-6-rabbitmq-1 rabbitmq-diagnostics -q check_running
podman exec --user rabbitmq social-network-homework-6-rabbitmq-1 rabbitmqctl list_queues name type consumers
```

## Масштабирование

### WebSocket

Балансировщик распределяет новые WebSocket-подключения между экземплярами API. Открытые соединения обслуживает принявший их экземпляр. Привязки RabbitMQ соответствуют активным пользователям на каждой реплике. Добавление экземпляра увеличивает доступный пул соединений без общей таблицы сессий. Реплики используют общий PostgreSQL и каталог ключей Data Protection. Общий брокер, БД и сетевой канал могут ограничить суммарную ёмкость.

#### Проверка в JMeter

Apache JMeter 5.6.3 и OpenJDK 17 в WSL Ubuntu. [План](../../scripts/homework-6.jmx) регистрировал автора и получателя через REST, устанавливал связь и открывал заданное число соединений с токеном получателя. После всех подключений автор отправлял один пост. Каждое соединение проверяло идентификатор поста, текст и идентификатор автора. Оба экземпляра API работали в обоих прогонах. Менялось распределение WebSocket-подключений при общей фоновой обработке.

| Прогон | Порт | Соединения | Получено кадров | От начала POST до кадра, мс, min / медиана / p95 / max | Handshake p95, мс |
| --- | ---: | ---: | ---: | --- | ---: |
| Одна реплика | 5086 | 40 | 40 | 99 / 100 / 102 / 103 | 66 |
| Две реплики | 5086 | 40 | 40 | 149 / 153 / 158 / 159 | 85 |
| Две реплики | 5087 | 40 | 40 | 149 / 153 / 158 / 158 | 85 |

Для доставки использовано поле `Latency` записей `WebSocket delivery` в JTL. Для установления соединения использовано поле `elapsed` записей `WebSocket handshake`. При расчёте p95 методом ближайшего ранга на каждом порту взято 38-е значение из 40 отсортированных замеров.

В первом прогоне выполнено 82 измерения, во втором — 162. Ошибок нет. При удвоении числа соединений p95 доставки увеличился со 102 до 158 мс. Все подключения получили кадр. Предельная пропускная способность и линейность её роста не измерялись.

Данные JMeter. Одна реплика — [JTL](jmeter/one.jtl), [статистика](jmeter/one-statistics.json). Две реплики — [JTL](jmeter/two.jtl), [статистика](jmeter/two-statistics.json).

Для повторения требуется JMeter с Java 17 и доступ к портам стенда из среды запуска JMeter. Создать каталог `TestResults/hw6`. Команды запускать из корня репозитория. Если JMeter отсутствует в `PATH`, вместо `jmeter` указать путь к `bin/jmeter` на Linux или macOS либо к `bin\jmeter.bat` на Windows. Для каждого прогона использовать новые имена файлов JTL и каталогов дашбордов.

```text
jmeter -n -t scripts/homework-6.jmx -Jsockets=40 -Jports=5086 -l TestResults/hw6/one.jtl -j TestResults/hw6/one.log -e -o TestResults/hw6/one-dashboard
jmeter -n -t scripts/homework-6.jmx -Jsockets=80 "-Jports=5086,5087" -l TestResults/hw6/two.jtl -j TestResults/hw6/two.log -e -o TestResults/hw6/two-dashboard
```

### RabbitMQ

1. При росте очереди `feed.materialize` увеличить число конкурирующих потребителей. Проверить число готовых и неподтверждённых сообщений, время материализации и нагрузку на PostgreSQL. Текущий consumer запрашивает по одной неподтверждённой задаче.
2. Для отказоустойчивости сформировать кластер из трёх узлов и распределить три реплики quorum queue. Для существующей очереди расширить состав реплик средствами `rabbitmq-queues` и проверить размещение. При потере одного узла два оставшихся образуют большинство. [Кластеризация RabbitMQ](https://www.rabbitmq.com/docs/4.2/clustering) · [Quorum queues](https://www.rabbitmq.com/docs/4.2/quorum-queues)
3. При насыщении лидера рабочей очереди разделить задачи между несколькими quorum queues по стабильному хешу UUID автора. Распределить лидеров через политику `queue-leader-locator=balanced`. Для существующих очередей `rabbitmq-queues rebalance quorum` перераспределяет лидеров. Состав реплик управляется отдельно. [Размещение лидеров](https://www.rabbitmq.com/docs/4.2/quorum-queues#rebalancing-replicas) · [Справочник rabbitmq-queues](https://www.rabbitmq.com/docs/man/rabbitmq-queues.8)

В локальном стенде работает один узел брокера с одной рабочей очередью. Кластеризация и распределение задач по нескольким очередям описаны как способ дальнейшего масштабирования.
