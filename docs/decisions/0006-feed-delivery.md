# ADR-0006. Отложенная материализация и WebSocket ленты

Статус: принято.

## Контекст

Публикация поста должна обновлять ленты друзей за пределами HTTP-запроса. Подписчик может открыть соединения на нескольких экземплярах API.

## Решение

В режиме RabbitMQ `PostStore` записывает пост и задачу outbox атомарно. `FeedDeliveryWorker` распределяет выборку задач между экземплярами через `FOR UPDATE SKIP LOCKED`. Запись удаляется после подтверждения публикации брокером. Долговечная quorum queue `feed.materialize` принимает задачи для конкурирующих потребителей. Материализация сохраняет уникальные пары получателя и поста в PostgreSQL. Добавление друга и материализация согласуются транзакционной advisory lock по идентификатору автора.

После фиксации пар worker публикует событие в direct exchange `feed.posted`. Ключ маршрутизации — UUID получателя без дефисов. Каждый экземпляр API обслуживает одну эксклюзивную временную очередь. Привязка создаётся перед открытием первого локального соединения пользователя и снимается после закрытия последнего. Локальные соединения получают событие из одной очереди экземпляра. Токены проверяются с общим каталогом ключей Data Protection.

## Следствия

Повтор обработки после сбоя оставляет адресные записи уникальными. Повторная доставка WebSocket-кадра возможна. Временная очередь и буферы сокетов ограничены. После разрыва клиент запрашивает REST-ленту. Отложенная обработка имеет отдельные границы масштабирования для PostgreSQL, рабочих потребителей и доставки WebSocket.

Один RabbitMQ обслуживает рабочие задачи и адресную отправку. Стенд запускается отдельно от конфигураций предыдущих заданий. Проверки приведены в [отчёте ДЗ №6](../homework-6/README.md).
