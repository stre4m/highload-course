# ADR-0005. Шардирование личных диалогов

Статус — принято. Дата — 2026-11-26.

## Контекст

Подсистема записывает сообщения на независимые экземпляры PostgreSQL. Основной запрос чтения выбирает переписку двух участников. Один пользователь может общаться существенно активнее остальных.

## Решение

Ключ диалога — пара UUID, отсортированная по возрастанию. UUID кодируются в сетевом порядке байтов и объединяются в 32 байта. Первые четыре байта SHA-256 интерпретируются как беззнаковое число в сетевом порядке. Остаток от деления на 1024 определяет виртуальный бакет. Карта бакетов задаётся в PostgreSQL по поколениям.

При отправке `DialogStore` выбирает владельца из последнего поколения и выполняет один `INSERT`. При чтении хранилище запрашивает один диапазон составного первичного ключа на каждом из уникальных владельцев бакета. Результаты объединяются по UUID сообщения и сортируются по времени записи и UUID.

## Следствия

Оба направления переписки используют один бакет. Сообщения пользователя с разными собеседниками хешируются по разным ключам и распределяются по узлам. Шардирование по UUID отправителя концентрирует записи активного пользователя и разделяет стороны диалога. Шардирование по UUID сообщения требует обращения ко всем шардам для чтения одного диалога. Выбранная схема ограничивает чтение владельцами бакета.

Пиковая нагрузка одного диалога ограничена записью на один узел. Смена владельца сохраняет прежний маршрут для чтения истории и увеличивает число запросов для перенесённых бакетов. Каталог участвует в каждой операции. Чтение полного диалога требует памяти пропорционально объёму истории.

Физическая миграция истории предусмотрена отдельной [процедурой](../homework-5/README.md#физический-перенос-истории-без-остановки).
